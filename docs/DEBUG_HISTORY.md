# Debug History

本文档记录 2026-04-28 到 2026-04-29 这一轮底盘控制调试的关键结论，重点保留“现象 -> 判断方法 -> 根因 -> 修复”的链路，方便后续继续定位同类问题。

## 1. 2026-04-28：先把链路稳定下来

### 1.1 串口状态回传异常

**现象**

- 上位机链路不稳定，状态帧和 IMU 帧容易互相干扰。
- 早期 `/chassis_status` 里出现过不符合物理语义的打包值泄漏。

**判断**

- 直接看 MCU 侧发送实现，发现多个任务都可能经 UART1 发数据。
- DMA + 共享发送缓冲的组合在并发下容易互相覆盖。

**修复**

- `component/src/pc_serial.c` 改成互斥保护的阻塞发送，优先保证协议稳定和可观测性。
- `/chassis_status` 回归物理语义：`linear.x = vx`，`linear.y = 0`，`angular.z = wz`。

**验证**

- Jetson 侧看到 `/chassis_status` 正常持续增长，`Recv` 增长、`Errors = 0`。

### 1.2 USB 枚举与设备识别

**现象**

- Linux 侧一度看不到可用串口设备，容易误判成 ROS 或串口名问题。

**判断**

- 该固件枚举的是原生 STM32 CDC ACM，不是 CH340。
- 关键枚举信息：`VID:PID = 0483:5740`。

**结论**

- 当 `/dev/ttyACM*`、`/dev/ttyUSB*`、`/dev/serial/by-*` 都没有对应设备时，应优先判定为 USB 枚举或物理连接问题，而不是上层软件配置问题。

## 2. 2026-04-28：ZLAC 故障需要可观测和可恢复

### 2.1 过压 / 过载故障

**现象**

- 运动过程中驱动器红灯闪烁，底盘刹停。
- ROS 串口链路本身仍然健康，`Recv` 继续增加，`Errors = 0`。

**判断**

- 需要把驱动器 `0x603F` 故障位直接暴露出来，而不是只看上层是否“像断线”。

**修复**

- 在 `Task/src/test_task.c` 中把首个非零 `0x603F` 锁存进 `/chassis_status.x/y` 对应的诊断位。
- 在 `component/inc/ZLA_Motor.h` 中只允许对 `0x0001` 过压和 `0x0008` 过载做低频软件恢复。
- 恢复流程包括：强制速度归零、限频复位 `0x6040 = 0x80`、检查 `0x2035` 母线电压、重新设速度模式/同步模式并使能。

**结果**

- 后续现场出现 `x = 8`、`y = 8` 时，可以直接判断前后驱动都报了 overload，而不是盲目追 ROS。

### 2.2 烧录路径收敛

**经验**

- Keil CLI 编译可稳定产出 hex。
- pyOCD 成功命令如下：

```powershell
.\.venv\Scripts\pyocd.exe flash -t stm32f103rc --connect under-reset --frequency 100000 --probe "ATK 20190528" -e chip "MDK-ARM\LY-020-USB-CDCsoftware\LY-020-USB-CDCsoftware.hex"
```

- 如果 pyOCD 和 Keil 都卡在 probe 连接，通常先看 CMSIS-DAP 是否真的被 Windows 枚举，而不是先改代码。

## 3. 2026-04-29：命令丢失后的安全停车

### 3.1 杀掉发布器后底盘不一定马上停

**现象**

- `/chassis_cmd` 发布器退出后，驱动器有时还保持上一帧非零速度。

**根因**

- `test_task.c` 早期只在 `both_ok` 路径里持续写目标值；一旦碰上错误或命令中断，零速命令未必能真正重发到 `0x60FF`。
- 当 MCU 认为 `target_vx/target_omega` 已经是 0 时，重复的零命令不一定触发新的写入。

**修复**

- 引入 `CHASSIS_CMD_TIMEOUT_MS = 300` 和 `command_timeout_stop_active` 路径。
- 超时后立即请求 safe stop，并提高停车斜率到：
  - 线速度 `1.0 m/s^2`
  - 角速度 `2.4 rad/s^2`
- 增加 `CHASSIS_STOP_BURST_COUNT = 5`，即使 MCU 内部已经认为目标为零，也会再显式重发一小段 `60FF = 0`。

**结果**

- 停止命令的可达性明显提高，重复零帧不再“看起来发了，实际上没真正落到驱动器”。

## 4. 2026-04-29：间歇性急刹并不总是电机真故障

### 4.1 诊断读超时被误当成致命错误

**现象**

- 用户在持续低速或中速运行中看到突然刹停，`/chassis_status.x/y` 经常出现 `-1`。
- 有时是后驱动，有时前后同时。

**关键判断**

- `-1` 代表 `ZLA_ERR_TIMEOUT`。
- 但要区分这到底是“诊断读取超时”还是“速度写入/心跳/NMT 真超时”。

**早期根因**

- 单次诊断 SDO 读取超时会被提升成 `last_error`，触发 safe stop 和 2 秒重初始化。

**修复演进**

1. 先对诊断读取错误加去抖：`CHASSIS_DIAG_ERROR_LIMIT = 3`。
2. 再把诊断类错误降级为“只观测、不停车”。
3. 诊断错误编码成 `-(100 + err)`，命令写错误编码成 `-(200 + err)`。
4. 速度写入失败、NMT/heartbeat 异常、真正致命 `last_error` 仍保留为直接负错误码。

**当前判读方法**

- `-101`：诊断读取超时，只说明观测面有噪声，不应直接解释成驱动失控。
- `-201`：命令写入层超时，要重点看 `ZLA_SetVelocity()` 路径。
- `-1`：仍然是致命 timeout，说明问题已经不只是基础诊断读取。

## 5. 2026-04-29：`-4` 不是 ROS 断链，而是 CAN 发送失败

**现象**

- Jetson 侧 `Sent` 正常增长、`Errors` 没明显增加，但 `/chassis_status.x/y` 出现 `-4`。

**判断**

- `ZLA_ERR_CAN_SEND = 4`，因此 `-4` 表示 STM32 到 ZLAC 的 CAN 发送失败。
- 这类问题通常应先查 CAN 物理层、驱动器供电和接线，而不是 ROS 串口服务。

**结论**

- 只要 MCU 还在稳定回传状态帧，就说明 USB/串口主链还在；`-4` 应优先按“MCU 到电机驱动”链路问题定位。

## 6. 当前推荐的现场排查顺序

1. 先看 USB CDC 是否真的枚举成功。
2. 再用 `serial_protocol_tester.py` 脱离 ROS 验证串口协议。
3. 再确认控制命令是否以足够频率持续发送，避免被 300 ms 超时安全停车击中。
4. 再看 `/chassis_status.x/y` 的数值语义：
   - `> 0`：真实驱动故障位
   - `-101/-102/...`：诊断读错误
   - `-201/-202/...`：命令层错误
   - `-1/-4/...`：致命 `last_error`
5. 最后才追 ROS service、topic bridge 或上层导航逻辑。

## 7. 仍需保持警惕的问题

- 诊断超时已经从“直接停车”降级为“只观测”，但如果未来看到持续 `-1`，说明仍有真正致命超时路径没有完全收口。
- 目前安全策略集中在 `test_task.c`，后续再加功能时不要把停车、故障恢复和错误升级逻辑分散到别处，否则现场会再次难以判读。
